## 첫 동작 목표

Pleos 차량용 화면에서 학원 한 곳을 선택한다. **바로 태우기**를 고르면 승하차점, **주차하고 데리러 가기**를 고르면 주차장 차량 입구를 보여준다. 사람 출입구는 그대로 유지한다. 운전자가 추천을 확인하면 순정 내비에 차량 도착점을 보낸다. 정차 후 최초 후보를 이용할 수 없다고 입력하면 대체 후보를 제안한다. 주차한 뒤 **여기서 만나요**에서 실제 만날 장소를 확인하고 휴대폰으로 전달한다.

## 구현 구조

Kotlin Android 앱 단일 모듈로 시작한다. UI는 도착지·출입구 선택, 추천 결과, 대체 후보, 정차 위치 공유로 구성한다. 설정은 로컬에 저장하고 시설 데이터는 JSON으로 동봉한다. 첫 시연은 별도 서버 없이 구동한다.

| 영역 | 구현 범위 |
| --- | --- |
| 추천 | 시설과 보행 출입구, 방문 모드, 차량·탑승 조건, 이번 방문에서 제외한 지점을 입력으로 받는다. 허용 조건을 먼저 적용하고 후보, 추천 이유, 후보 없음 사유를 반환한다. |
| 시설 데이터 | 시설, 보행 출입구, 차량 접근점, 두 지점 사이 보행 연결을 구분한다. 승하차 허용 시간, 주차 운영시간, 높이 제한, 무단차 확인 상태와 출처를 저장한다. 시연용 파일과 실제 확인된 시설 자료를 구분한다. |
| Pleos 내비 | 추천 결과의 차량 접근점으로 요청한다. 요청 대기·성공·실패를 화면 상태로 표시한다. 대기 중 중복 요청을 막고, 사용자가 후보를 바꾼 뒤 도착한 이전 응답은 새 후보의 결과로 표시하지 않는다. |
| 차량 상태 | 좌석 점유를 읽을 수 있으면 저장 옵션을 제안한다. 값 없음과 빈 좌석을 구분한다. 접근이 불가하면 수동 선택을 유지한다. 주행 제한 신호에 맞춰 입력·공유 조작을 제한한다. |
| 정차 위치 공유 | 사용자가 확인한 위치와 출입구·층·기둥 번호로 문구를 생성한다. 휴대폰에서 QR 등으로 문구와 지도 링크를 열고 수신자를 선택하는 흐름을 검증한다. 전송 확인이 없으면 발송 완료로 표시하지 않는다. |

### 추천 판단

- **바로 태우기**에서는 해당 시간·차량에 이용 조건이 확인된 승하차점을 우선한다. 후보가 없으면 주차장을 제시한다.
- **주차하고 데리러 가기**에서는 이용 가능한 주차장의 차량 접근점을 고르고 같은 사람 출입구까지의 보행 연결을 보여준다.
- 첫 후보를 이용할 수 없으면 현재 방문에서 제외하고 다시 계산한다. 운영 종료, 차량 높이 초과, 필수 무단차 미확인은 추천 조건에 반영한다. 후보가 모두 제외되면 안내 가능한 후보가 없음을 표시한다.
- 지하에서는 확인된 층·구역·기둥 번호와 보행 안내를 사용한다. 정차 위치 신호가 불확실하면 사용자가 지점을 직접 확인한다.

## 개발 환경과 첫 작업

1. **Codex Cloud**에서 공식 NaviHelper 샘플의 빌드 설정을 확인한다. SDK 의존성 설치, Gradle 빌드, JVM 단위 테스트를 실행한다. Cloud에서 에뮬레이터 실행을 시도할 때는 `/dev/kvm` 접근과 `emulator -accel-check`를 확인한다.
2. **맥북 Android Studio**에 Pleos Connect Automotive AVD를 준비한다. 공식 설치 가이드의 v2.1.0·API 34 이미지를 기준으로 시작하고, 실제 사용 버전과 화면 규격을 기록한다. Cloud의 AVD가 부팅되지 않으면 같은 브랜치를 맥북에서 검증한다.
3. 공식 샘플로 일반 목적지 한 곳을 먼저 확인한 뒤, 차량 접근점 두 곳의 요청과 순정 내비 핀을 비교한다. 좌표만으로 요청하는 경우와 POI 식별자가 필요한 경우를 확인한다. 정확한 진입점을 전달하지 못하면 지원되는 접근점과 별도 보행 안내를 사용하고 시연 범위를 기록한다.
4. 도착자리 Android 프로젝트를 초기화하고 가상 시설 한 곳에 사람 출입구 하나, 승하차점과 주차장 입구를 구성한다. 테스트용으로 라우팅 가능한 좌표가 필요하면 별도 테스트 지점을 확인하고 실제 시설의 승하차 허용 정보로 노출하지 않는다. 내비 요청 모의 모드로 추천 UI를 점검한 뒤 Pleos 연동을 붙인다.
