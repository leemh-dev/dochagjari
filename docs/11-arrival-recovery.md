# 자동 도착 알림 복구 계약

v0.2.0의 목적은 확정한 픽업 요청을 재시작 후 복원하면서 같은 세션의 중복 발송을 막는 것입니다. 공급자 수락은 실제 휴대폰 수신 확인과 다릅니다.

## 요청과 서버 결과

- `POST /v1/arrivals`는 기존 UUID·등록 수신자 ID·좌표·단서·정차/위치 확인·입력 출처에 `delivery_mode: mock | sens`를 추가합니다. 생략 기본값은 `mock`이며 서버 실행 모드와 다르면 409입니다. 이전 클라이언트로 SENS를 사용하는 경우 새 클라이언트로 갱신해야 합니다.
- UUID 하나는 수신자 하나와 고정된 요청 내용에 묶입니다. SQLite 쓰기 트랜잭션 안에서 같은 UUID를 먼저 확인하므로 수신자·좌표·단서·입력 출처·모드를 바꾼 요청은 새 공급자 호출 없이 409가 됩니다.
- POST 응답과 인증된 `GET /v1/arrivals/{session_id}/{recipient_id}`는 `status`, `request_hash`, `delivery_mode`, `input_source`를 반환합니다. POST에는 `duplicate`, GET에는 `provider_id`도 있습니다. 이 정보로 저장된 요청과 결과를 대조합니다.
- 요청 지문은 `arrival-v2`, UUID, 수신자 ID, 위도, 경도, 단서, `true`, `true`, 입력 출처, 모드 순서입니다. 각 필드를 UTF-8 바이트 수와 `:`로 접두한 뒤 SHA-256을 구합니다. 좌표는 big-endian IEEE754 double의 16자리 hex이며 ±0은 +0으로 정규화합니다. Kotlin·Python 공통 테스트 벡터로 차이를 검증합니다.
- DB에는 요청 지문·상태·모드·시각·수신자 ID 등 처리 메타데이터만 저장합니다. 좌표·단서·실제 전화번호·접근 토큰은 DB 요청 본문으로 추가 저장하지 않습니다. 수신번호는 서버 환경의 등록 정보로만 공급자에 전달합니다. 기존 수신자 ID를 다른 전화번호로 재할당하지 말고 새 ID를 사용합니다.

## 앱의 영속 기록과 재개

- 앱 전용 저장소의 원자적 파일 교체로 확정 위치·단서·세션·등록 수신자 ID·발송 방식/서버 주소·입력 출처·동의 시각과 처리 상태를 저장합니다. 저장 실패 시 요청을 시작하지 않습니다. API 토큰과 실제 전화번호는 저널에 넣지 않습니다.
- 처리 상태는 표시 문구와 분리된 enum입니다. 최초 전송과 재시작 모두 서버 GET부터 실행합니다. 모의 로컬 완료는 네트워크를 사용하지 않습니다.
- GET 404이고 서버 예약을 한 번도 확인하지 않은 요청만 기존 동의와 고정 내용을 대조한 뒤 같은 UUID로 POST합니다. 이미 확인한 기록이 사라지면 재발송하지 않습니다.
- 서버의 `pending`·`unknown`은 결과 확인 필요 상태를 유지합니다. 401·통신 실패·다른 지문/모드·이전 형식의 응답에서도 POST를 이어가지 않습니다. 토큰은 메모리에만 두며 재시작 후 없으면 설정 필요 상태입니다.
- 전송 전 예약을 저장한 서버가 공급자 호출 직전에 종료되면 `pending`으로 남습니다. 공급자 호출 여부를 추측해 재시도하지 않습니다. **중복 방지를 위해 자동 복구가 발송 완료를 보장하지 않는 경우**입니다. 서버·공급자 기록을 수동 대조해야 합니다. 복구를 위해 DB를 삭제하면 안 됩니다.
- UI에서 동의를 해제하면 영속 기록에도 반영합니다. 이후 조회는 가능하지만 404를 받아도 POST하지 않습니다. 이미 시작한 요청을 취소하거나 전달된 문자를 회수할 수는 없습니다. 미해결 요청을 새 세션 ID로 재발송하지 않습니다.
- 확정 후에는 위치·수신자·서버/모드를 고정합니다. 토큰 입력이나 결과 조회로 이를 변경하지 않습니다. 성공·명확한 실패 또는 아직 요청하지 않은 초안에서만 새 픽업 세션을 만들 수 있습니다. 새 세션에는 동의를 다시 확인합니다.

## 이전 기록과 설정 저장

- v0.1 앱 저널은 좌표·대상이 없으므로 추측해서 복원하지 않습니다. 이전 모의 완료·공급자 수락은 보존하고, 불명확한 기록은 수동 확인 상태로 둡니다. 기존 서버 DB에는 nullable 모드 열을 추가하며, 모드 증거가 없는 기록을 자동 복구 성공으로 취급하지 않습니다.
- 프로필 저장은 애플리케이션 수명의 단일 큐에서 순서대로 수행합니다. 화면에 선택값을 즉시 보여줄 수 있지만 DataStore 쓰기 완료 전에는 `저장 중`으로 표시합니다. 완료한 revision과 실제 저장값을 별도로 보관하고 실패 시 `저장 실패`·재시도를 제공합니다.
- ViewModel 종료는 저장 큐를 취소하지 않습니다. OS가 프로세스를 강제 종료한 경우에는 마지막으로 **저장 완료**된 값의 복원을 보장하며 아직 저장 중인 변경을 완료한 것으로 표시하지 않습니다.

검증 명령·성공 여부는 [검증 기록](08-verification.md), 실행 이력은 [개발 일지](10-development-log.md)에 기록합니다.

## 실제 Android HTTP 복구 증거 — 2026-11-12

[2c2feb0 PR CI43134026080](https://github.com/leemh-dev/dochagjari/actions/runs/43134026080)에서 실제 앱 UI와 loopback SERVER_MOCK를 연결했습니다. 서버 DB 저장 후 응답을 보류하고 앱/서버를 종료·재시작해 같은 세션/요청 지문·위치·대상·모드를 복원했습니다. 토큰은 비어 있었고 재입력/결과 확인 후 GET200으로 복구했습니다. GET404→POST1회→재시작 GET1회, DB행/지문 동일·공급자0회입니다. DB 삭제/새 세션 재발송을 사용하지 않았습니다. [원본3장·검증 경계](evidence/android-http-recovery/README.md)와 [정제 추적](evidence/android-http-recovery/summary.json)을 제공합니다. 실제 공급자 수락/휴대폰 수신이나 모든 pending/unknown 조합의 기기 검증을 뜻하지 않습니다.
