## 구현 순서와 작은 완료 단위

각 구현 단위의 **Cloud 검사와 Mac Pleos 확인**은 [실행절차36](36-cloud-mac-development-workflow.md)의 서로 다른 열로 기록한다. Mac M1/8GB·외장SSD와 기존실측을참고하고미연결이면Cloud작업을계속한다. 새브랜치의실제기기검사는단계별로새증거를남긴다.

| 순서 | 구현 단위 | 완료 확인 |
| --- | --- | --- |
| 1 | 다중 탑승 프리셋/이번 구성의 모델·저장·기존 단일 구성 이행 | 실제 저장 재조회·즉시종료/새PID·실패/연속변경·기존 설정/방문/알림 보존 |
| 2 | 목적지와 독립된 탑승 설정 화면, 모드 선택/이번만 적용/저장 갱신·제안 | 목적지 없이 사용, 혼자/아이/가족 변경, 점유/역할/미지원 분리, 건너뛰기·주행 제한 |

첫 코드 작업은 **1번의 모델/저장/이행**이다. 새 데이터 저장소를 덧대기 전에 ProfileRepository의 기존 순차 writer/revision/SAVED/persisted 계약과 옛 파일을 읽고 이행 경계를 정한다. 프리셋/이번 구성/센서 관측은 분리하고 탑승세션을 방문/알림 세션과 합치지 않는다. 기존 데이터 삭제나 기본값 초기화로 이행을 대신하지 않는다.

실제 음성/차량 신호가 없으면 텍스트 입력과 TEST점유로 개발을 계속한다. 첫 단계에 확인되지 않은 Gleo/앞좌석/외부카메라 접근을 완료 조건으로 묶지 않는다. 현재 미구현 AI시설자료보완 worker는 별도 후속 단위로 두고 음성·탑승 설정과 한꺼번에 완료 약속하지 않는다.

앱 코드를 바꾸면 새 버전/코드 식별과 실제 산출물 기준을 기록한다. 이번 브랜치 분리 커밋에서는 앱/APK를 변경하지 않았다. 기존 통과 결과를 새 브랜치의 새 검사로 재사용하지 않으며 변경 범위에 맞는 의미 있는 저장/회귀/기기 검사를 수행한다.

## PR와 GitHub 기록

새 Draft PR은 기존 브랜치를 base로 한다. PR#1은 그대로 열어두며 자동 병합하지 않는다. 이후 PR#1이 병합/변경되면 base의 실제 상태를 먼저 확인하고 새 PR을 적절히 재지정한다. 새로운 main 기반으로 갈아타기 위해 이미 작성한 변경을 버리거나 이력을 강제로 덮어쓰지 않는다.

기능 단위 커밋/푸시·docs10의 실제 절차·docs08의 새 검증 수준·증거/artifact·PR 설명을 갱신한다. APK를 바꾸면 실제파일 SHA256/버전/코드/개발서명 또는 unsigned를 기록한다. 시안/설계 검증과 실제앱·일반Android·Pleos·실차의 결과를 구분한다.

현재 완료는 브랜치 분리·시안/앱 보존 대조·새 작업 순서/프롬프트 정리다. 다중 탑승/음성/새 패널의 실제 구현이나 영상 제작을 이번에 수행했다고 표시하지 않는다.
