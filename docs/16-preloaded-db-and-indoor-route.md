# 사전 시설 DB와 에뜨와 매장 실내 경로선

2026-11-13 KST · 사용자 추가 요구/개발 설계. 시설 수집·DB·앱 구현 완료 증거가 아니다. [고정 시나리오 계획](15-hyundai-department-demo-plan.md), [개발계획](07-development-plan.md), [검증 기록](08-verification.md)을 함께 따른다.

## 확정 시나리오 — 2026-11-13 UTC

사용자가 목적 매장을 **현대백화점 판교점 5층 에뜨와**로 확정했다. 출발지는 현대자동차 양재 사옥이다. [공식 층별 안내 조회 증거](evidence/hyundai-store-check/README.md)로 판교점/에뜨와/5F 유·아동 구역을 확인했다. 게이트 번호·주차 구역·엘리베이터·도면 보행 경로와 거리, 앱 DB/추천/주차·귀환 구현은 아직 별도 조사/개발 대상이다. 과거 아가방 조회 결과는 이력으로 보존하며 두 브랜드를 별칭으로 합치지 않는다.

## 고정 요구

- 현대자동차 양재 사옥 출발 → 현대백화점 판교점의 **에뜨와 매장** 방문 → 주차 위치 기억 → 귀환을 목표로 한다. 이전 나이키/아가방 후보는 사용자 선택에 따라 변경했다.
- 공식 층별 안내에서 판교점 에뜨와의 입점과 5층 유·아동 구역을 확인했다. 엘리베이터/게이트·실내 도면 경로와 축척은 추가 조사한다.
- 앱은 매번 웹을 검색하지 않는다. 자주 쓰는 시설·매장·층·게이트·주차 구역·엘리베이터·보행 연결·출처를 미리 DB에 저장하고 저장된 데이터로 추천한다.
- 주차 게이트 번호와 엘리베이터 번호/명칭은 별도 정보다. 실제 시설이 번호 대신 명칭을 쓰면 원래 이름을 표시하며 번호를 만들어 붙이지 않는다.

## 데이터 수집과 이용을 분리한다

**운영/개발 수집 작업:** 공식 시설 안내·도면·공공데이터·최신 관련 리뷰 수집 → AI 추출/시설·층 식별 → 근거 대조 → DB 버전 발행.

**앱 이용:** 로컬 DB 조회 → 매장/조건별 연결 계산 → 안내 카드·실내 경로선 → 확인된 게이트 내비 전달. 일반 조회에는 웹 검색/LLM 호출이 필요하지 않다. 자연어 입력의 매장 식별을 붙이더라도 기존 별칭/매장 검색을 우선 재사용한다.

- 초기 한 지점은 출처를 검토한 데이터와 도면/경로 자산을 앱에 사전 제공하고 Room/SQLite로 조회한다. 다른 DB 제품 도입이나 새 상시 서버를 선행 조건으로 삼지 않는다.
- 최신성은 매 요청 재검색 대신 데이터 수집/갱신 단계에서 관리한다. 필드별 `source`, `sourceUpdatedAt`, `checkedAt`, `refreshDueAt`, `verificationStatus`, 데이터셋 버전을 둔다. 갱신 주기는 정보 성격과 실제 제공 주기에 맞춰 설정한다.
- 출시/시연 초기에는 명시적 검토·갱신 명령으로 버전을 발행할 수 있게 한다. 주기 수집은 별도 작업으로 추가하며 이미 스케줄러가 동작한다고 표시하지 않는다.
- 공식 변경 공지·폐점/이전·오류 신고·갱신기한 도래는 재확인 대상으로 만든다. 네트워크가 되면 버전 확인 후 변경된 레코드/자산만 내려받도록 확장한다. 실패 시 마지막 검증 버전을 유지하고 오래된 상태를 표시한다.
- DB에 없는 매장/연결은 조회 실패/확인 필요를 표시하고 중복 제거한 갱신 작업으로 보낸다. 예외적 온라인 조회를 지원하면 출처·확인 상태를 붙여 검토 후 재사용한다. 사용자 요청마다 같은 검색을 반복하지 않는다.
- 접근 필수 조건이나 폐쇄 여부가 불명확하면 과거 DB 값만으로 이용 가능/무단차 충족을 확정하지 않는다. 혼잡·주차면 점유 등 변동 정보는 정적 연결과 별도로 시각·유효기간을 관리한다.
- 방문/주차 개인 기록은 시설 공통 DB와 분리한다. 공통 시설 DB 교체가 개인 방문 기록이나 기존 SMS outbox를 삭제하지 않는다.

## 앱 안내

아래 문장은 게이트/엘리베이터 번호 조사 전의 **표시 형식**이며 시설 안내 사실이 아니다.

> “[확인된 주차 게이트명]으로 진입 → [주차 층·구역]에 주차 → [엘리베이터 번호/명칭] 이용 → 5층 하차 → 에뜨와까지 표시된 보행 경로로 이동.”

차량 게이트 안내와 건물 보행 출입문을 구분한다. 출발 전 추천 요약을 보여주고 주행 중 조작 제한을 유지한다. 상세 도면은 정차/방문 준비 화면에서 제공한다. 확보되지 않은 구역/연결은 빈칸을 추정으로 채우지 않고 확인 필요로 표시한다.

## 엘리베이터에서 에뜨와까지 경로선

목표는 해당 유아동 매장층의 **확인된 층별 안내도 위에 엘리베이터 출구부터 에뜨와 입구까지 보행 가능한 경로선을 표시**하는 것이다. 실내 현재 위치 추적/실시간 파란 점 기능은 별도이며 이번 경로선을 측위 성공으로 표시하지 않는다.

- `FloorPlan`: 시설/층, 안내도 자산, 원본 출처/확인일, 도면 버전, 이미지 크기/좌표계, 축척 확인 상태.
- `IndoorNode`: 같은 도면 버전에 맞는 엘리베이터 출구·복도 분기·매장 출입구 좌표. 이미지 내 정규화 좌표를 쓰고 화면 확대/축소에도 같은 변환을 적용한다.
- `WalkEdge`: 실제 연결된 복도 구간의 꺾인 선 좌표, 통행 방향/제한, 계단·문·단차·유모차/휠체어 확인 상태, 근거, 길이/단위/측정 방식.
- `IndoorRoute`: 엘리베이터 출구에서 매장 출입구까지 연결된 노드/간선으로 경로 계산. 매장 내부나 벽을 가로지르는 단순 직선은 쓰지 않는다. 같은 도면 버전의 경로만 겹쳐 그린다.
- 도면 축척이나 실제 구간 길이가 검증됐을 때만 “약 ○m”를 표시한다. 축척 미확인이면 경로선·방향/분기 안내까지만 표시하고 이미지 픽셀을 미터로 간주하지 않는다. 이동 시간도 근거 없이 계산하지 않는다.
- 실제 안내도를 확보하면 정확한 위치/경로를 대조한다. 원본 지도 대신 재작성한 개략도를 쓰는 경우 개략도임을 표시한다. 도면 공개/재사용 범위에 따라 공개 저장소에는 출처/허용된 자산만 두고 필요한 경우 링크나 자체 개략도를 사용한다.
- 지도나 통로 연결을 확보하지 못해도 텍스트 안내/저장/귀환 개발은 계속한다. 실제 층별 경로선은 근거 확보 전 완료로 표시하지 않는다. 테스트 도면은 기능 검증용이며 실제 에뜨와 동선으로 표시하지 않는다.

## 구현 순서/검증

1. 에뜨와 입점/층과 주차·엘리베이터 연결, 층별 안내도 확보. 출처/누락 필드를 기록한다.
2. 시설 DB 스키마와 검토한 seed 데이터, 로컬 조회/별칭 검색/버전 관리. 동일 목적지 반복 조회와 오프라인 조회에서 외부 검색 호출 없이 결과가 나오는지 확인한다.
3. “게이트→주차 구역→엘리베이터→층” 안내 카드와 확인된 게이트 내비 전달. 지점/브랜드 혼동·DB에 없는 매장·오래된 정보·필수 접근 조건 미확인을 처리한다.
4. 층별 지도 뷰와 노드/보행 간선, 경로선·확인 가능한 거리 표시. 실제 복도와 선 대조, 벽 통과 없음, 확대/축소 정합, 연결 없음, 도면 버전 불일치, 축척 미확인, 동행 조건 경로를 검사한다.
5. 기존 입차/영상 관측·주차 위치 저장·귀환과 연결한다. 재시작 후 같은 방문 및 사용 도면/데이터 버전을 유지한다. 버전 변경 시 이전 위치의 연결을 재확인한다.
6. 에뮬레이터 화면을 단계별 공유하고 실제 DB/사전 자료·실제 도면/개략도·경로선/측위·실제 SDK/테스트 입력을 구분해 녹화한다. 앱 코드가 바뀌면 새 APK의 버전·코드·해시·서명을 기록한다.

우선순위는 DB 조회와 텍스트 안내가 필수, 실제 안내도 경로선은 도면/통로 확보 시 추가다. 경로선 작업으로 핵심 도착·주차·귀환 흐름을 전체 중단하지 않는다. 이번 문서는 설계이며 실제 DB/경로선 구현과 주차/엘리베이터 연결 확인은 아직 별도 작업이다.
