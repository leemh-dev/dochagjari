# 새 방향의 코드 보존과 정리 기준

2026-11-14 UTC. 사용자가 과거 구현을 지워 새 개발의 혼선을 줄일지 문의했다. **일괄 삭제보다 공통 기반 보존·기존 화면 교체·개발자 기능 분리·과거 지시 정리를 우선한다.** 새 브랜치 `feat/arrival-context-ux`와 PR#2에서 작업하며 기존 PR#1/시안/기준코드는 유지한다.

이번에는 현재 호출 관계를 정적으로 조사하고 문서 진입점/다음 프롬프트를 정리했다. 앱 소스/데이터/테스트/워크플로를 삭제하거나 이동하지 않았고 새 빌드/기기 검사를 수행하지 않았다. 정적 검토를 실행 오류 재현이나 완전한 미사용 코드 분석으로 표시하지 않는다.

## 현재 확인한 실제 호출 관계

- `MainActivity.onCreate → ProductApp`가 앱 기본 진입점이다.
- `ProductApp`는 `developer` 분기에서 `ArrivalApp(model, initialTab)`를 호출한다. 따라서 예전 화면은 현재 개발자 도구이며 즉시 삭제할 수 있는 무호출 코드가 아니다.
- `AppModel`은 `facilities.json`을 읽고 `AppServices`의 profiles/outbox/guidance를 관찰한다. 예전 시설 파일/알림 타입을 UI 취향만으로 지우면 초기화/저장복구에 영향을 줄 수 있다.
- `.github/workflows/android.yml`은 서버/진단 검사와 캡처·복원 스크립트를 사용한다. 정리 대상으로 보이는 스크립트도 workflow/테스트 연결을 함께 확인해야 한다.

위 내용은 코드 읽기로 확인한 의존 관계다. 이번 조사만으로 **안전하게 바로 삭제해도 된다고 확정한 앱 소스 목록은 없다.** 목적은 옛 기능을 계속 제품 중심에 두는 것이 아니라, 필요한 책임을 먼저 옮긴 뒤 겹치는 구현을 제거하는 것이다.

## 삭제/교체 단위의 완료 기준

1. 새 구현이 대신할 책임과 기존 파일/키/화면 호출/자산/검사 참조를 적는다.
2. 새 동작과 데이터 이행을 구현하고 실제 저장값·실패/연속변경·종료복원·기존방문/확정알림 보존을 확인한다.
3. 호출자를 새 구현으로 전환한 다음 무참조가 된 코드/옛 화면/낡은 선택기만 같은 단위에서 제거한다. 화면이 사라졌다는 이유로 데이터 읽기 호환까지 삭제하지 않는다.
4. 관련 단위/회귀·lint/빌드, 가능한 기기 검사를 실행한다. APK가 바뀌면 실제 버전/코드/해시/서명을 기록한다.

새 소스구조의 후보는 탑승설정·도착안내·지도표현·차량/내비 어댑터·저장·개발자도구다. 한 번에 모든 패키지/파일명을 바꾸는 작업을 첫 단계로 추가하지 않는다. 먼저 [설계33](33-occupant-modes-and-trip-context.md)의 다중 프리셋/이번 구성 저장·이행을 완료한다.
