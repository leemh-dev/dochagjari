# 증상 전1분부터 종료까지 · 구간 기록과 정비소 인계

2026-11-14 UTC. [48의 초기 기획](48-voice-symptom-recorder-plan.md)을 사용자 요구에 따라 보완한다. 사용자는 ‘증상 기록해 줘’의 **직전1분부터 ‘종료해 줘’까지** 운행/환경을 기록하고, 고객과 정비사가 이 기록으로 대화하며, 정비소에서 스캐너 연결 시 바로 열리는 흐름을 제안했다. 이번은 설계 보완/공식 자료 조사이며 구현·기기·스캐너 연동 검증은 아니다.

## 서비스 정의와 시연

**운전자가 증상을 느낀 구간의 전후 상황을 보존하고, 정비사가 고객의 설명과 차량 관측을 시간순으로 함께 보는 서비스.** 기존 단일 시점 snapshot을 구간 기록으로 확장한다. 고장 원인을 자동 확정하는 서비스로 설명하지 않는다.

1. 운전자가 기록 준비를 명시적으로 켠다. 지원/허용된 차량 상태를 최근60초의 임시 순환 버퍼에 유지한다. 상시 차내 음성/영상 녹음과 다르며 전체 주행을 서버로 업로드하지 않는다.
2. 14:32:00에 ‘증상 기록해 줘’가 앱의 검증된 호출 경로로 도착하면, 14:31:00 이후 실제로 확보된 데이터만 같은 session ID로 보존하기 시작한다. 증상 설명과 차량 상태는 출처가 다르다.
3. 14:33:20에 ‘종료해 줘’가 인식되면 상태 데이터 수집을 중지하고 해당 구간을 저장한다. 실제 범위는 전60초+기록80초=140초다. 이전48의 고정 후15초 예시는 이 요구로 대체한다.
4. 정차 후 원문/타임라인/관측 공백을 확인하고 저장ACK를 확인한다. 종료 실패·STT 지연·앱 종료·권한 철회·저장 실패를 정상 완료로 처리하지 않는다.
5. 정비소에서 고객이 공유할 구간을 선택한다. 정비사는 기록을 열어 ‘이 소리가 여기서 났나요?’, ‘이때 공조가 켜져 있었네요’처럼 함께 대화한다. 스캐너에서 확인한 현재 DTC/기존 freeze frame은 별도 출처/시각으로 비교한다.

예시 시각/데이터는 설계용이며 실측이 아니다. ‘증상 기록’/‘종료’의 Gleo 호출, 앱 STT 입력, 일반Android TEST 입력은 각각 검증 수준을 표시한다.

## 직전1분을 남길 수 있는 조건

명령을 들은 후에 수집을 처음 시작하면 과거1분은 복원할 수 없다. **사전 기록 준비와 그동안 SDK callback을 실제 수신한 이력**이 필요하다. 준비한 지20초면 최대20초만 있고, 프로세스가 죽었거나 SDK가 끊겨 있었으면 해당 구간은 없다. 마지막 값 하나를 복제해 연속 운행 데이터처럼 만들지 않는다.

순환 버퍼의60초와 기록 세션의 영속 저장을 구분한다. 준비 중 미선택 과거는 만료시키고 선택된 구간만 저장한다. 구현 시 시간 기준은 monotonic 수신 시각과 표시용 wall clock을 함께 사용한다. 명령 발화 시각, STT 결과 수신 시각, 기록 trigger 시각도 구분한다. 소급 시작점을 사용자에게 보장하기 전에 음성 처리 지연과 실제 버퍼 범위를 확인한다.

앱 비활성/화면 꺼짐/다른 앱 실행 중에도 수집이 보장되는지는 별도 실행·정책 확인이 필요하다. Android foreground service를 추가하면 Pleos의 모든 백그라운드 수집 문제가 해결된다고 가정하지 않는다. 초기 시연은 명시 준비/지원되는 앱 실행 상태로 제한한다. 종료·권한 철회·앱 종료 후 자동 재개하지 않는다.

‘종료해 줘’는 영속 기록 종료와 준비 버퍼도 중지하는 보수적 기본값으로 제안한다. 종료 후 준비를 유지하는 옵션은 사용자 의사를 확인하는 후속 UX로 남긴다. 무한 기록을 막을 시간/용량 상한, 남은 공간 부족/마지막 저장 실패 표시가 필요하며 실제 상한값은 측정 후 정한다.

FusedLocation1.1.3 공식 소개에는 `isSupported/getLastKnownLocation/registerFusedLocationCallback/unregisterFusedLocationCallback`과 `LocationData`의위경도·고도·방향·신뢰도·timestamp가있다. `FUSED_LOCATION`권한이필요하며별도권한페이지는Android일반권한/백그라운드정책을보장하지않는다고명시한다. 이문서에서는웹문서만확인했고바이너리/기기/이동궤적수신은시험하지않았다.

제품문구는 ‘주변·도로·운행 모든 데이터’ 대신 **‘공개SDK로 확인 가능한 차량 상태와 허용된 위치·환경 자료를 시간순으로 기록’**을 사용한다. 모든정보를얻는최종비전과현재구현범위를분리한다.

## 스캐너를 꽂으면 바로 열리는 목표

현재앱의SQLite기록은인포테인먼트앱저장소에있다. OBD/GDS스캐너가ECU와통신하는것과임의앱저장소를읽는것은다른연결이다. 공개Pleos자료에서 앱기록을ECU에저장하거나OBD를통해노출하는API, GDS가Pleos앱기록을자동조회하는공개계약은확인하지못했다. 절대불가능이라는뜻은아니며정식연동근거가필요하다.

- **1차 구현/시연:** 고객이선택한보고서/PDF를정비사에게보여준다. 공유/QR/웹뷰어를추가한다면그전송·접근동의·만료·실제정비사단말열람을구현/시험해야한다. 로컬PDF공유조차Pleos대상앱가용성이미검증이므로자동완료로표시하지않는다. 스캐너가있으면별도진단화면과나란히본다.
- **정식 연동 목표:** 스캐너연결→차량/정비접수건식별→고객공유동의확인→그접수건의선택기록조회→같은시각축에서비교. GDS/GIT/현대측지원인터페이스, 인증/권한, 식별자연결, 기록포맷/단위/시각정의가필요하다. VIN만안다고고객기록을열수있는설계는하지않는다.
- **구분:** 앱시연용정비사뷰어와GDS진짜화면은다르다. 임의JSON을MSR/GSR파일로이름만바꿔GDS호환으로표시하지않고, fake스캐너연결을실제연동으로연출하지않는다. ECU쓰기/진단권한우회는하지않는다.

## 새로 확인한 기존 정비 장비 기능

GIT 공식 GDS Smart 안내에는 recorded data 조회/VCI II운행기록복사가있다. GDS Viewer안내는MSR/GSR을GDS Smart/GENESIS Smart/KDS2.0에서열수있다고설명한다. TQR공식안내에는음성·PDF·센서·freeze frame증거첨부가있다. 따라서‘정비장비에기록/자료첨부가전혀없다’는차별화는맞지않는다.

다만이자료는 **GDS계열자체기록/정비사보고기능**의근거이며, 일반운전자가Pleos에서전1분부터음성으로표시한구간을정비소가기존스캐너연결만으로자동조회한다는근거는아니다. 해외공식지원문서의기능을한국모든정비소/전차종설치확인으로확대하지않는다. 차별성가설은정비소방문전에발생하는간헐적증상을운전자가쉽게보존하고정비대화에연결하는흐름이다.
