# 내비와 이어지는 도착자리 UX · 시안 v1

2026-11-13 UTC. 사용자 검토에 따라 **6단계 기능 기반 → UX 설계/Android 적용 → 7단계 최종 연속시연**으로 우선순위를 조정한다. 기능 검증 완료와 제품 UX 완성을 구분한다. 이 커밋은 설계/호스트 프로토타입이며 Android 코드/DB/APK0.8.0/8·84acdd3를 변경하지 않는다.

## 문제와 설계 목표

현재 앱은 상태/저장 검증용 화면이다. 긴 설명·테스트 버튼·UUID/SQLite 같은 구현 정보가 실제 방문 안내를 가리고, 지도는 별도 미리보기로 떨어져 있다. 내비에서 주차/매장 안내로 이어지는 사용 경험은 아직 완성되지 않았다. UI를 최종 영상 뒤의 장식 작업으로 미루지 않는다.

목표는 **차량 내비로 시설까지 → 입차 확인 → 주차/승강 연결 안내 → 5층 에뜨와 → 주차 기억/귀환**의 연속성이다. 사용자에게 필요한 한 문장·하나의 주요 행동과 큰 공간 시각화를 우선한다. 글자는 지도의 의미를 설명하는 보조다.

기존 Mac Pleos 원본의 흰색 콘텐츠/검정 시스템 영역·큰 요소를 참고한다. 공식 최신 디자인 토큰/컴포넌트 적합성을 인증한 것은 아니며 'Pleos 참고형 제안'이다. 클러스터·시스템바/공조·내비 제어를 앱이 임의로 복제/덮지 않는다.

5층 경로는 기존 catalog14점/IndoorFloorPlan 블록을 재사용한다. 주변 매장은 회색 덩어리로 배경화하고 유아휴게실/대여·엘리베이터·에뜨와만 우선 표기한다. 미확인 주차장 도면·기둥·게이트·승강기 호기를 그려 넣지 않는다. 주차층↔승강 연결이 나중에 검증되면 별도 계층으로 추가한다.

## 내비 연결 방식 — 두 가지를 혼동하지 않는다

**기본 A: 공식 요청 + 정상 앱 전환.** 현재 NaviHelper 목적지 요청/이벤트와 앱 자체 Compose 지도를 연결한다. 도로 안내는 순정 내비가 맡고, 허용된 사용자 진입점/앱 전환으로 도착자리 안내를 연다. 실제 SDK/순정 핀·전환·자동입차는 아직 별도 실기 검증 대상이다. 사용자 입력/정상 권한 외 임의 foreground/overlay를 요구하지 않는다.

**조건부 B: 내비 내부 카드/분할/지도 통합.** 공식 확장 지점/템플릿/embedding·전달 데이터·앱 표시 영역/주행 정책이 확인된 경우만 설계한다. NaviHelper의 목적지 요청이 곧 지도 임베딩 권한은 아니다. 프로토타입 도로 장면은 B의 구현 성공도 순정 내비 화면 복제도 아닌 구성 모형이다. Android 적용 전 공식 문서·샘플/실행 근거로 A/B의 가능한 범위를 확정한다. 지원 안 되는 B를 시연에서 실제처럼 합성하지 않는다.

## 공통 UX 규칙

- 콘텐츠 지도/카드 대비를 먼저 검토한다. 주간은 밝은 중립색/검정 주요 버튼·파란 경로를 제안한다. 야간/실제 Pleos DPI와 폰트 크기는 Android 적용 때 실제 환경에서 재조정한다. 1280×800 호스트 시안은 AAOS 인증/터치 적합성 실측이 아니다. 실제 Pleos 앱의 가용 영역/Insets·DPI를 읽어 운전자 클러스터·시스템 영역을 침범하지 않는 레이아웃을 적용해야 한다. 넓은 영역은 지도/카드 병렬, 좁은 영역은 단계별 카드로 조정한다.
- 주요 행동 하나, 보조 행동 최대 두 개. 설계 목표 터치 최소64dp/큰 본문24sp부터 검토하되 실제 장치 기준으로 검증한다. HTML px를 Android dp 적합성으로 간주하지 않는다.
- 주행/unknown은 상세 지도·문자 단서·입력/설정을 숨기고 짧은 안내만 표시한다. 명시 주차/입차·편집은 정차 후다. 닫기는 항상 가능하다.
- 재생은 정차 시에만. 호스트 시안4.5초는 검토용 값이며 아직 Android 확정 규격이 아니다. reduced motion은 전체 선을 정적으로 표시한다. 이동점/사람 아이콘을 현재 위치처럼 쓰지 않는다.
- 닫기/백그라운드/종료/권한 철회/이동 후 자동 재개 없음. 시안은 이를 모의한 것이며 실제 DB/자원 해제 검사는 기존 앱의 별도 근거를 따른다.
- 저장 중/확인 실패/저장 확인을 사용자 언어로 보여준다. UUID·서버 응답·SQLite/DataStore·원문 프레임/테스트 조작은 개발자 화면/증거로 옮긴다. 출처/미확인은 짧은 표기와 상세보기로 유지하고 숨겨 사실처럼 꾸미지 않는다.
- 단계 표시에서 '주차 위치'와 '5층 매장행 미리보기'를 구분한다. 실제 주차가 끝나기 전에도 정차 중 매장행 동선을 볼 수 있으며 이것이 입차/주차 완료를 만들지 않는다.

## 산출물과 현재 검토 수준

[독립 프로토타입](ux/arrival-v1/prototype.html): 한 파일로 내려받아 브라우저에서 열 수 있다. 외부 CDN/API·실제 저장·실제 내비/차량 호출은 없다. 상단/하단의 장면·주행 상태 버튼은 검토 도구이며 제품 탭이 아니다. 모든 전환/기록은 브라우저 메모리 안의 모의다.

호스트 Chromium/Playwright로6장면·파란선 재생과 완료·주행 상세/조작 제한·닫기 시 경로 제거를 확인했다. 8 PNG 원본과 [검토 보고](ux/arrival-v1/review.json)를 보관한다. Android/Pleos 화면이나 기기 검사로 세지 않는다. 최초 file URL은 관리 정책에 의해 차단되어 설정을 바꾸지 않고 정상 loopback HTTP로 렌더링했다.

## 다음 구현 순서/수용 기준

1. 실제 Pleos 공식 문서/샘플로 앱 영역·내비 전환·분할/카드 지원을 조사하고 A/B를 근거로 확정한다. 이 조사 없이 B를 구현 완료로 약속하지 않는다.
2. 이번 시안 검토에서 화면 구성/정보량/상호작용을 조정하고 Android에 옮길 규격을 고정한다. 정차/주행/unknown·닫힘·미확인/저장중/실패·reduced motion을 포함한다.
3. 기존 AppModel/방문·설정·알림 저장 계약을 재사용해 Compose 화면을 적용한다. 기능 재작성이나 DB 초기화로 화면 변경을 해결하지 않는다.
4. 동일 APK에서 실제 화면·전환/애니메이션을 검증한 뒤 7단계 연속시연/제출 준비를 수행한다. UX 호스트 성공과 Android/Pleos 성공을 구분한다.

Sol급 코딩 모델로 설계/Compose 구현을 진행할 수 있다. Astra급 별도 검토는 복잡한 연동/설계 충돌이 남을 때 선택한다. 지도/모션은 Compose가 담당하고 대형 LLM을 UI 렌더링에 넣지 않는다. M1/8GiB에서 대형 로컬 모델을 필수로 하지 않는다. 앱 내부 AI 자료보완 worker는 별도 미구현으로 유지한다.
